## 二、失败过的度量方法（最容易重走的弯路）

判断棋子底盘色是否漂移，**以下三种方法各自都导出过看似精确、实则错误的结论**：

1. **取整盘均值（含主体）** —— 会把"白色生物是白的"误判成"底盘被调亮"。曾据此把白狼/白蛇/白虫团/Bill 四款列为最高优先返修，四款全是误判：按正确口径它们的底盘分别是 79.1 / 71.3 / 68.9 / 69.0，全在正常带内（全体中位 69.1）。
2. **用面积反推半径** `R=sqrt(N/π)≈0.855` 再取 `0.74–0.82×R` —— 环带实际落在 0.63–0.70 半画布，与主体重叠。这也是上一条的根因，并且顺带把 stone-troll 的越界平均掉了。
3. **跨图中位建模分割主体与底盘** —— 会把底盘边缘的光照差异误判为主体。

**收敛后的唯一口径**（`tools/check_token_style.py` 实现的就是这个）：

```
环带 0.72 ≤ d ≤ 0.84，d = hypot(x+0.5-64, y+0.5-64)/64，仅计 alpha ≥ 128
按角度切 8 扇区，扇区 0 从左起顺时针：sector = min(7, int((atan2(dy,dx)+π)/(2π)*8))
每扇区取亮度中位，L = 0.299R + 0.587G + 0.114B
每扇区减去冻结基线同扇区值
取这 8 个偏移的中位数
```

**第 5 步取中位而非均值是关键**：它对 1–2 个被主体侵入或接触阴影污染的扇区免疫。

## 三、已被排除的三种解释

"巨魔系统性偏暗、四足系统性偏亮"这个结论曾被三次质疑，三次都用数据排除：

- **光照梯度** —— 按扇区归一化后家族偏移不但没消失反而更清晰（巨魔 −12.5、四足 +7.9、其余 21 款 −2.3）
- **接触阴影** —— 阴影只压暗背光侧，而巨魔在 7–8 个扇区全向偏暗，prox 和 stone-troll 是 8/8
- **环境遮蔽（AO）** —— AO 应随离主体距离衰减，实测巨魔**外带比内带更暗**（−12.2 vs −9.4），方向相反

**一条用错过的论证**：曾以"两族 `外−内` 都约 −3 ⇒ 存在共有径向项"作为证据。这是错的——每条带都已减去全体同扇区中位，共有项必然被抵消，`外−内` 只是相对量（其余 21 款实测 +1.1，全体中位 +0.8 ≈ 0）。排除 AO **只靠外带比内带更暗这一点**。

## 四、门控的设计理由

`tools/check_token_style.py`（提交 `fb8e816`）。

| 判据 | 阈值 | 级别 |
| --- | --- | --- |
| 母版原生 alpha | 存储 mode 须为 RGBA/LA/PA 或带 tRNS 的 P | 阻断 |
| 圆盘越界 | 最大不透明半径 ≤ 0.867 | 阻断 |
| 底盘偏移 | 8 扇区去光照偏移中位 ∈ [−8, +8] | 阻断 |
| 主体侵入外环 | 单扇区偏移 − 本款中位 ≤ +20 | 警告 |
| 四角透明 | alpha = 0 | 阻断 |

**基线必须冻结，不得每次重算。** 当前值 `S0=72.09 S1=71.16 S2=64.66 S3=62.97 S4=65.21 S5=67.05 S6=74.33 S7=76.42`，由当时 37 款计算。若随贴图集合重算，每加入一张漂移的新图都会把基线拉过去一点，门控会**随时间自我失效**——典型的反馈回路失效。`baseline --recompute` 会打印重算值与冻结值的逐扇区差供核对。若将来返修现有美术，需显式重算并记录溯源。

**容差为什么是 ±8**：现有 37 款中 −5~+6 只有 46% 合规、−8~+8 有 70%、−10~+10 有 84%。±8 既能排掉真正的尾部（v1/v2 巨魔暗端、v4 四足与虫群亮端），又不会让新图与多数现有邻居失配。这是从现状归纳的基线，不是设计目标。

**豁免（grandfather）只对当时的 37 款、只对两项历史欠账**（`disc_overflow`、`base_drift`）。母版 alpha 与四角透明任何情况下都不放行。报告会提示当前 25 款已达标、可从名单移除。

**已知钝角**：`subject_intrusion` 取扇区中位，**对只占窄角度扇区的特征不敏感**。实例：`skeleton warrior` 的头盔顶盖压在圆盘斜边上，但实测 +2.75 是 46 款里第五低。不要把低数值读成"离盘边很远"。

## 五、refinement 逃生口

`art_tasks.py` 对已映射身份默认拒收，规范允许的唯一例外是"专门的 refinement brief"。该路径原先在工具里**不存在**（报错文案指向它但代码不支持），`7b0b29e` 把它实现为必须声明的 `refinement` 块：

- `supersedes` 须等于 catalog 里的真实 token id
- `previous_batch` 须命名已用完配额的批次
- `design_change_reason` ≥ 80 字符，且必须是**设计方向改变**而非"再试一次"
- `evidence` 须为按 SHA-256 钉住的非空列表，**钉子在 `record` 阶段重新校验**（事后改旧回执凑理由会被发现）

**残留风险**：80 字符的理由是软检查，硬约束在钉住的证据。这条路每次被用到都应复核一眼该批次的 `BRIEF.md`。反向漏洞已堵（给未映射身份声明 refinement 同样拒收）。

## 六、生产链路

```sh
python3 tools/run_imagegen.py status   art/production/handoffs/BATCH/ASSET
python3 tools/run_imagegen.py generate art/production/handoffs/BATCH/ASSET --saved art/BATCH/masters/ASSET-v1.png            # 预演，不花额度
python3 tools/run_imagegen.py generate art/production/handoffs/BATCH/ASSET --saved art/BATCH/masters/ASSET-v1.png --execute
python3 tools/run_imagegen.py repair   art/production/handoffs/BATCH/ASSET --execute
```

链路：`codex exec -i <参考图> --output-schema --output-last-message` → **溯源校验**（产物须在 `~/.codex/generated_images/` 之下）→ 母版 alpha → 128px 导出 → 风格门控 → `art_tasks.py record` 入库。

**溯源校验是防线不是形式**：`codex exec` 跑的是完整 agent，它可能自己写代码画图。该目录只有内置 ImageGen 会写。但它证明的是"文件由内置工具写出"，**不证明画面内容没被诱导**。

**codex 侧的已知失败模式**：提示词未明确要求透明时，ImageGen 可能返回**不含 alpha 的 RGB 图**，甚至把背景画成棋盘格冒充透明。已实测复现（C0b 棕鼷返修图），`templates/repair.txt` 的对应要求在 `7b0b29e` 补齐。**但该模式并非每次复现**——包装器自检时刻意不提透明，返回的仍是 RGBA。这道检查照常必要。

**预算规则**：单包 codex 调用总数硬顶 `max_attempts`（1 或 2），失败的调用同样占额，按 `call-*` **目录**数计（目录在发起前建好，记账崩掉也不白送），**没有 `--force` 开关**。

**任务包的 `sources` 不要钉住本轮会被修改的文件** —— 包装器自检就因此被 `record` 正确拒收过。
